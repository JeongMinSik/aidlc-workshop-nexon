# NFR Design Patterns - Unit 2 (Frontend)

## 1. 복원력 패턴 (Resilience Patterns)

### 1.1 네트워크 재시도 패턴
```typescript
// API 호출 실패 시 재시도 전략
interface RetryConfig {
  maxRetries: 3;
  baseDelay: 1000;       // 1초
  maxDelay: 10000;       // 10초
  backoffMultiplier: 2;  // 지수 백오프
}

// 적용 대상: 주문 생성, 상태 변경 등 중요 API
// 미적용 대상: 메뉴 조회 등 읽기 전용 API (캐시 폴백)
```

### 1.2 SSE 재연결 패턴
```
연결 끊김 감지
    → 즉시 UI 상태 업데이트 ("연결 끊김" 표시)
    → 3초 대기 → 재연결 시도 #1
    → 실패 → 6초 대기 → 재연결 시도 #2
    → 실패 → 12초 대기 → 재연결 시도 #3
    → 실패 → 24초 대기 → 재연결 시도 #4
    → 실패 → 48초 대기 → 재연결 시도 #5
    → 5회 실패 → "수동 새로고침 필요" 안내
    → 재연결 성공 → 전체 데이터 리로드 (일관성 보장)
```

### 1.3 Graceful Degradation 패턴
| 장애 상황 | 대응 | 사용자 경험 |
|-----------|------|------------|
| API 서버 다운 | 캐시된 메뉴 표시 + 오프라인 배너 | 메뉴 탐색 가능, 주문 불가 |
| SSE 연결 끊김 | 폴링 폴백 (30초 간격) | 실시간성 저하, 기능 유지 |
| 이미지 로드 실패 | 플레이스홀더 이미지 표시 | 메뉴명/가격은 정상 표시 |
| localStorage 불가 | 메모리 상태만 사용 | 새로고침 시 장바구니 초기화 |

## 2. 성능 패턴 (Performance Patterns)

### 2.1 캐싱 전략 (Service Worker)
```
┌─────────────────────────────────────────────┐
│              Cache Layers                    │
├─────────────────────────────────────────────┤
│ L1: Memory (React State)                    │
│     - 현재 세션 데이터                       │
│     - 장바구니, 인증 상태                    │
├─────────────────────────────────────────────┤
│ L2: Service Worker Cache                    │
│     - 앱 셸 (HTML/JS/CSS)                   │
│     - 메뉴 데이터 (5분 TTL)                  │
│     - 이미지 (24시간 TTL)                    │
├─────────────────────────────────────────────┤
│ L3: localStorage                            │
│     - 장바구니 데이터                        │
│     - 인증 토큰                             │
│     - 테이블 설정 정보                       │
├─────────────────────────────────────────────┤
│ L4: Network (API Server)                    │
│     - 최신 데이터 (Source of Truth)          │
└─────────────────────────────────────────────┘
```

### 2.2 렌더링 최적화 패턴
| 패턴 | 적용 대상 | 효과 |
|------|----------|------|
| `React.memo` | MenuCard, OrderCard, TableCard | 불필요한 리렌더링 방지 |
| `useMemo` | 총액 계산, 필터링된 목록 | 비용 높은 계산 캐싱 |
| `useCallback` | 이벤트 핸들러 | 자식 컴포넌트 리렌더링 방지 |
| 가상화 (선택) | 긴 주문 목록 | DOM 노드 수 제한 |
| 코드 스플리팅 | 페이지별 | 초기 로드 크기 감소 |

### 2.3 이미지 최적화 패턴
```typescript
// 메뉴 이미지 로딩 전략
// 1. loading="lazy" — 뷰포트 진입 시 로드
```

## 3. PWA 패턴 (Offline-First)

### 3.1 Service Worker 라이프사이클
```
Install → 앱 셸 캐싱 (HTML, JS, CSS, 폰트)
Activate → 이전 캐시 정리
Fetch → 요청 유형별 전략 적용:
  - 앱 셸: Cache First
  - API (GET): Network First → Cache Fallback
  - API (POST/PUT/DELETE): Network Only → Background Sync Queue
  - 이미지: Cache First (24시간 TTL)
```

### 3.2 Background Sync 패턴 (주문 생성)
```
주문 생성 요청
    → 네트워크 가용? 
        → Yes: 즉시 전송 → 성공/실패 처리
        → No: IndexedDB 큐에 저장 → "네트워크 복구 시 전송됩니다" 안내
            → 네트워크 복구 감지 → 큐에서 꺼내 전송 → 결과 알림
```

### 3.3 캐시 무효화 전략
| 데이터 | TTL | 무효화 조건 |
|--------|-----|------------|
| 앱 셸 | 빌드 버전 변경 시 | 새 배포 시 자동 업데이트 |
| 메뉴 데이터 | 5분 | 관리자 메뉴 변경 시 (수동 새로고침) |
| 이미지 | 24시간 | URL 변경 시 |
| 주문 데이터 | 캐시 안 함 | 항상 최신 (Network Only) |

## 4. 상태 관리 패턴

### 4.1 Context 분리 패턴
```
App
├── AuthContext (인증 상태 — 변경 빈도 낮음)
│   ├── CartContext (장바구니 — 변경 빈도 높음, 고객앱만)
│   │   └── Pages...
│   └── OrderContext (주문 상태 — SSE 업데이트, 관리자앱만)
│       └── Pages...
```

**분리 이유**: Context 변경 시 하위 전체 리렌더링 방지
- AuthContext 변경 → 전체 리렌더링 (드물게 발생)
- CartContext 변경 → 장바구니 관련 컴포넌트만 리렌더링
- OrderContext 변경 → 대시보드 관련 컴포넌트만 리렌더링

### 4.2 Optimistic Update 패턴 (관리자앱)
```
사용자 액션 (예: 주문 상태 변경)
    → 즉시 UI 업데이트 (낙관적)
    → API 호출
        → 성공: 확정 (변경 없음)
        → 실패: 롤백 + 에러 토스트
```

## 5. 보안 패턴 (Frontend)

### 5.1 토큰 관리 패턴
```
로그인 성공 → 토큰 localStorage 저장
    → 모든 API 요청에 Authorization 헤더 자동 첨부
    → 401 응답 수신 → 토큰 삭제 → 로그인 화면 리다이렉트
    → 16시간 만료 체크 (1분 간격 타이머)
        → 만료 10분 전: 갱신 시도 (선택)
        → 만료: 자동 로그아웃
```

### 5.2 입력 검증 패턴 (이중 검증)
```
클라이언트 검증 (즉시 피드백)
    → 통과 → API 전송
        → 서버 검증 (최종 권한)
            → 실패 → 서버 에러 메시지 표시
```

### 5.3 라우트 가드 패턴
```typescript
// ProtectedRoute 컴포넌트
// 1. 인증 상태 확인
// 2. 미인증 → 로그인/설정 페이지 리다이렉트
// 3. 권한 확인 (관리자앱: role 체크)
// 4. 권한 부족 → 접근 거부 페이지 또는 리다이렉트
```
